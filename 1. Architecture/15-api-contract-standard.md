# 15 — API Contract Standard

This document deepens Volume 1 `05-api-architecture.md` into a binding, implementation-ready
contract. Where Volume 1 established the shape, this document fixes the exact rules.

## 1. Base Conventions (Reaffirmed and Fixed)

- Base path: `/v1`. Major-version-only in the path; minor/patch changes are additive and
  unversioned.
- Transport: HTTPS/TLS 1.2+ only; HTTP requests are rejected at the edge (redirect or hard reject,
  an infrastructure-prompt choice, never silently served over plaintext).
- `Content-Type: application/json` for all request/response bodies except signed-URL binary
  uploads (which go directly to object storage, not through `core-api`).
- Resource naming: plural nouns, hierarchical nesting only where ownership is hierarchical (see
  Volume 1 `05-...md` §1 examples).
- Methods: `GET`, `POST`, `PATCH`, `DELETE`. No `PUT`.

## 2. Headers (Canonical, Required/Optional)

| Header | Direction | Required | Purpose |
|---|---|---|---|
| `Authorization: Bearer <JWT>` | Request | Required except auth endpoints | Authentication |
| `Idempotency-Key` | Request | Optional but strongly recommended on all unsafe methods; **required** on `POST /v1/conversations`, `POST /v1/conversations/{id}/members`, `POST /v1/media/uploads` | Generic request-level dedup |
| `X-Correlation-Id` | Request/Response | Optional on request (server generates if absent); always present on response | Tracing |
| `traceparent` | Request/Response | Optional (propagated if present; generated by the edge if absent) | Distributed tracing (W3C Trace Context) |
| `X-RateLimit-Limit` / `X-RateLimit-Remaining` / `X-RateLimit-Reset` | Response | Always present | Rate-limit visibility |
| `Retry-After` | Response | Present on `429` and `503` | Backoff guidance |
| `Deprecation` / `Sunset` | Response | Present on deprecated endpoints | Deprecation signaling (RFC 8594) |
| `ETag` | Response | Present on cacheable single-resource `GET`s (e.g., `GET /v1/profiles/{userId}`) | Conditional-request support |
| `If-None-Match` | Request | Optional, paired with `ETag` | Conditional `GET` → `304` |

Cookies are not used for API authentication (Volume 1 `09-...md` §4's CSRF-avoidance rationale).

## 3. Standardized Error Contract (Fixed Schema)

```json
{
  "error": {
    "code": "MESSAGE_VALIDATION_FAILED",
    "message": "The message body exceeds the maximum allowed length.",
    "correlationId": "b3a1c2e0-6b0e-4e2a-9b0a-7e2b1e6c2d3f",
    "retryable": false,
    "details": [
      { "field": "body", "issue": "max_length_exceeded", "limit": 4096 }
    ],
    "metadata": { }
  }
}
```

| Field | Required | Rule |
|---|---|---|
| `code` | Yes | Stable, `SCREAMING_SNAKE_CASE`, never changes meaning once shipped (a new failure mode gets a new code, not a redefinition of an old one) |
| `message` | Yes | Human-readable, safe for display, English by default with client-side localization by `code` (the server does not localize error text) |
| `correlationId` | Yes | Matches `X-Correlation-Id` |
| `retryable` | Yes | Boolean — tells the client whether a mechanical retry (same request, no changes) could plausibly succeed (`true` for `503`/`429`/network-classified errors; `false` for `400`/`403`/`404`/`422`) |
| `details` | No | Present for validation errors (`400`); array of field-level issues |
| `metadata` | No | Present only for specific codes that need extra structured context (e.g., `RATE_LIMIT_EXCEEDED` includes `retryAfterSeconds` here in addition to the `Retry-After` header, for clients that only inspect the body) |

**Never included**: stack traces, internal file paths, database error text, infrastructure
hostnames, or any detail that would help an attacker map internal architecture. Internal errors
(`500`) always return a generic `message` ("An unexpected error occurred.") with the real cause
only in server-side logs, keyed by `correlationId` for support lookup.

### 3.1 Canonical Error Code Namespaces

| Prefix | Domain |
|---|---|
| `AUTH_*` | Authentication (`AUTH_INVALID_CREDENTIALS`, `AUTH_TOKEN_EXPIRED`, `AUTH_TOKEN_INVALID`) |
| `SESSION_*` | Session/device (`SESSION_REVOKED`, `SESSION_NOT_FOUND`) |
| `CONVERSATION_*` | Conversations/groups (`CONVERSATION_NOT_FOUND`, `CONVERSATION_MEMBER_LIMIT_EXCEEDED`) |
| `GROUP_*` | Group-specific (`GROUP_INSUFFICIENT_ROLE`, `GROUP_LAST_OWNER_CANNOT_LEAVE`) |
| `MESSAGE_*` | Messaging (`MESSAGE_VALIDATION_FAILED`, `MESSAGE_EDIT_WINDOW_EXPIRED`, `MESSAGE_NOT_FOUND`) |
| `MEDIA_*` | Media (`MEDIA_CONTENT_TYPE_NOT_ALLOWED`, `MEDIA_SIZE_LIMIT_EXCEEDED`, `MEDIA_NOT_READY`) |
| `CONTACT_*` | Contacts/blocking (`CONTACT_BLOCKED`) |
| `RATE_LIMIT_*` | Rate limiting (`RATE_LIMIT_EXCEEDED`) |
| `VALIDATION_*` | Generic schema validation not owned by a specific domain code above |
| `INTERNAL_*` | Unexpected server errors (`INTERNAL_SERVER_ERROR`) |
| `DEPENDENCY_*` | Upstream dependency unavailable (`DEPENDENCY_UNAVAILABLE`, mapped to `503`) |

## 4. Pagination Contract (Fixed)

### 4.1 Cursor Pagination (Default and Required for High-Volume Resources)

Applies to: conversation message history, conversation list, member list (for large groups),
search results, audit log queries, notification delivery log queries.

- Request: `?limit=<n>&cursor=<opaque>`.
- `limit`: server-enforced max (default cap 100; per-endpoint default when unspecified is
  documented per endpoint, architectural default 50).
- `cursor`: opaque, base64-encoded, server-constructed from the keyset position (e.g.,
  `{serverAcceptedAt, id}` for messages). Clients must treat it as opaque; the server may change
  its internal encoding across a minor release without that being a breaking change, as long as
  a cursor issued by version N is still valid when passed back within its retention window (the
  server does not need to support cursors older than, e.g., 24 hours across some future
  re-encoding — this bound must be documented per-endpoint if a re-encoding ever occurs, since it
  is currently not exercised in this volume).
- **Sort guarantee**: fixed, index-backed order per endpoint (documented per endpoint; e.g.,
  message history is always `conversationSequence DESC`). No client-specified arbitrary sort on
  cursor-paginated endpoints.
- **Invalid cursor**: `400 VALIDATION_INVALID_CURSOR` — never silently falls back to the first
  page (that would surprise a client mid-pagination).
- **Deleted-record behavior**: a record deleted between page fetches is simply absent from
  subsequent pages (its keyset position is skipped); this does not corrupt pagination because the
  cursor encodes a *position*, not a record reference.
- **Duplicate prevention across pages**: guaranteed by keyset pagination's nature — a record is
  returned at most once for a given, unchanging cursor chain, because the ordering key is
  immutable per record (`conversationSequence`, `serverAcceptedAt`) or, for resources ordered by
  a mutable field, the pagination key additionally includes a stable tiebreaker `id`.
- **Concurrent-write behavior**: a new record inserted with a position *before* the client's
  current cursor (rare — only possible for out-of-order server-side inserts, which do not occur
  for message history since `conversationSequence` is strictly increasing) will not retroactively
  appear on an already-fetched page; a new record inserted *after* the cursor's position appears
  naturally on the next page fetch, which is the expected, non-surprising behavior for a live
  feed.

### 4.2 Offset Pagination — Explicitly Permitted Exceptions

Offset pagination (`?page=&pageSize=`) is permitted **only** for small, bounded, low-write-rate
admin/reporting resources where total result count is useful to display and the underlying table
size is architecturally bounded or filtered to a small scope:

- `GET /v1/admin/reports?status=open&page=` (open reports are a bounded operational queue, not a
  high-volume table).
- `GET /v1/admin/moderation-actions?page=` (bounded by admin action volume, far lower than
  message volume).

No other endpoint may use offset pagination. Any endpoint backed by `message`, `audit_event`,
`notification_delivery_log`, or the search index is cursor-only, without exception.

## 5. Idempotency Contract (Fixed)

### 5.1 Generic `Idempotency-Key` Mechanism

| Property | Rule |
|---|---|
| Key format | Client-generated UUIDv4 |
| Storage | `IdempotencyRecord(key, userId, endpoint, requestHash, responseStatus, responseBody, createdAt)` |
| Lifetime | 24 hours from `createdAt`; expired keys are eligible for garbage collection and may be reused after expiry (treated as a new request) |
| Scope | `(userId, endpoint, key)` — the same key from two different users, or against two different endpoints, is not considered a collision |
| Request matching | The server additionally hashes the request body (`requestHash`); if the same key is replayed with a **different** body, the server returns `409 IDEMPOTENCY_KEY_CONFLICT` rather than silently executing either version — this catches client bugs where a key is accidentally reused across logically different requests |
| Replay behavior | Same key + same body hash → server returns the stored `responseStatus`/`responseBody` immediately, without re-executing side effects |
| Conflicting-request behavior | Same key + different body hash → `409 IDEMPOTENCY_KEY_CONFLICT` |

### 5.2 Domain-Specific Idempotency (Message Send)

`clientMessageId` (Volume 1 `03-...md` §5.2, reaffirmed): permanent, not time-boxed like the
generic header mechanism, because a client may retry a send across a much longer offline period
than 24 hours (see `19-synchronization-and-offline.md` §2) and must still be protected from
creating a duplicate message on eventual reconnect.

### 5.3 Idempotency for Other Named Operations

| Operation | Idempotency mechanism |
|---|---|
| `CreateConversation` | `Idempotency-Key` header (required) — creating a conversation twice due to a double-tap/retry must not create two conversation objects |
| `UploadMedia` (initiate) | `Idempotency-Key` header (required) — prevents allocating two `MediaAsset` rows (and two presigned URLs) for one logical upload intent |
| `AddMember` / `RemoveMember` | Natural idempotency via the underlying unique constraint (`conversations.group_member (conversation_id, user_id)`) — a repeated `AddMember` for an already-present member is a no-op success (`200`, not `409`); a repeated `RemoveMember` for an already-absent member is also a no-op success, not an error, because the end state the caller wants (member not present) already holds |
| Notification dispatch | `(eventId, pushTokenId)` dedup key at the queue/worker layer (Volume 1 `07-...md` §5, `08-...md` §3.2) — not a client-facing `Idempotency-Key`, since clients do not directly trigger notification dispatch |
| Administrative operations (role grant/revoke, restriction application) | `Idempotency-Key` header required on all admin mutating endpoints, given the higher cost of duplicate execution (e.g., accidentally applying a restriction twice should not double-penalize or create duplicate audit ambiguity) |

## 6. Content Negotiation and Validation

- Only `application/json` is accepted/produced; a request with an unsupported `Content-Type`
  receives `415 UNSUPPORTED_MEDIA_TYPE` (using the standard error envelope with
  `code: VALIDATION_UNSUPPORTED_MEDIA_TYPE`).
- Request bodies are validated against a strict schema (unknown fields rejected, not silently
  ignored, to catch client/server contract drift early) using a schema-validation layer (e.g.,
  `class-validator`/`zod`-equivalent) at the API boundary before any handler logic runs.
- Validation failures return `400` with `details` populated per-field.

## 7. Rate-Limit Response Contract

`429` responses:
```json
{
  "error": {
    "code": "RATE_LIMIT_EXCEEDED",
    "message": "Too many requests. Please slow down.",
    "correlationId": "...",
    "retryable": true,
    "metadata": { "retryAfterSeconds": 12 }
  }
}
```
with `Retry-After: 12` and `X-RateLimit-*` headers set consistently with the body.
